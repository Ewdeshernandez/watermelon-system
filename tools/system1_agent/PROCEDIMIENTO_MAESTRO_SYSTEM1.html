1. Resumen ejecutivo

Bently System1 no expone la onda cruda por SQL — solo por "Export to CSV" en su GUI. Un robot RPA (s1_rpa_export.py, pywinauto) automatiza ese export por coordenadas de pantalla, corriendo DENTRO de la VM de cada turbina. El HOST (único con internet) lee los CSV por recurso compartido UNC y los sube a Supabase. La web (Watermelon Live → Live Monitoring → Advanced Analysis) los muestra como onda / espectro / órbita. Todo corre solo cada hora y se recupera solo tras cualquier reinicio.

Estado 2026-10-20
SGT300A: 100 % hands-off VALIDADO (reinicio real → auto-run → nube). SGT300B: replicado igual, falta solo el reinicio final de prueba. Blindaje anti-cruce activo en ambas.

3. Flujo de datos extremo a extremo

  1. VM — WM_export (cada hora): export.bat → --nav (selecciona máquina en el árbol → Plots → Export CSV1) → exporta 8 bearings (clic-derecho en cada gráfica → Export to CSV → Save As) a C:\WM_wave\csv, luego cambia a Export CSV2 → 7-8 gearbox a C:\WM_wave\csvgb.
  2. HOST — WM_upload (cada hora): lee \\<IP-VM>\C$\WM_wave\csv y \csvgb, empareja X/Y por cojinete, sube a Supabase bucket dynamic_raw/<asset>/<AAAAMMDD>/<HHMMSS>__<punto>.csv.
  3. Nube → Web: core.dynamic_raw.list_captures lista el bucket; Advanced Analysis dibuja onda/espectro/órbita.
  4. Colector Modbus (paralelo): overalls + RPM → API → Live Monitoring (online/alarmas).

4. PROBLEMAS Y SOLUCIONES (catálogo completo)

P1 · Tras reiniciar no exporta (Save As queda vacío / 0/8)
Windows Server, tras un apagado/reinicio inesperado, saca el modal "Shutdown Event Tracker" ("Why did the computer shut down unexpectedly?"). Ese cuadro roba el foco y el nombre que el robot teclea para el Save As cae en SU caja (quedaba Problem Id: C:\WM_wave\csv\1yd.csv) → Save As vacío → #32770 no apareció → 1er canal falla → cascada "no hallé Export to CSV". Solo pasa tras reiniciar; a mano después ya no está el cuadro. NO es el teclado.
Fix: desactivar el tracker por registro (VM) + el robot lo cierra solo en _dismiss_dialogs. 
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Reliability" /v ShutdownReasonOn /t REG_DWORD /d 0 /f
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Reliability" /v ShutdownReasonUI /t REG_DWORD /d 0 /f
P2 · Datos CRUZADOS — bearings ↔ gearbox invertidos (GRAVE)
El clic del robot sobre la sub-pestaña a veces la arrastra y reordena (Export CSV1 ↔ Export CSV2). Si quedan invertidas, la coordenada fija cae en la hoja equivocada → BRG1 termina con data de 4XD GEARBOX y GB4 con 1XD TURBINA. Intermitente (A alternó cruzado/correcto todo un día: 54 cruzados / 50 OK). Peligroso: diagnóstico equivocado.
Fix (doble, commits 6bfae4c + 34d4466): (1) Blindaje: el robot lee Point Name del CSV recién exportado y verifica que el canal real corresponde al tile esperado; si no → borra el archivo y marca cruce (jamás sube cruzado). (2) Auto-corrección: al detectar cruce, activa la OTRA posición de pestaña (357↔472) y reintenta el mismo tile → sale 8/8 sea cual sea el orden. Verificación: # point vs # point_name del CSV subido.
P3 · Save As teclea mal (\→} , :→ñ) — teclado Latin American
El guest revierte a Latin American en cada reinicio; el RDP/VMware anidado remapea y corrompe la ruta del Save As.
Fix (commit f063420): el robot fuerza en-US POR VENTANA justo antes de teclear, vía Win32 LoadKeyboardLayoutW("00000409") + PostMessage(WM_INPUTLANGCHANGEREQUEST). Inmune al layout de la sesión. Respaldo: Set-WinUserLanguageList en-US -Force en export.bat.
P4 · Save As se congela con "_" en la ruta
El underscore es inteclable en el RDP anidado → nombre corrupto → freeze.
Fix: gearbox a C:\WM_wave\csvgb (SIN underscore), NUNCA csv_gb. Bearings a csv. Debe coincidir VM ↔ config del host.
P5 · Tras reiniciar, System1 no selecciona la máquina (base en vista inicio)
System1 abre la base pero queda en la vista de inicio; la pestaña Export CSV1 no existe hasta seleccionar máquina + Plots → --expall solo no la halla.
Fix (commit 97918f1): flag --nav que clica por coord Máquina(árbol) → Plots → Export CSV1, ANTEPUESTO en export.bat (se garantiza en cada corrida, no depende del arranque).
P6 · "Could not open selected enterprise" al abrir la base tras reiniciar
El servicio "System 1 Data Server" estaba en Manual → Stopped tras boot → el Open fallaba.
Fix: Set-Service "System 1 Data Server" -StartupType Automatic (+ Start-Service). Las otras (Data Acquisition / Enterprise) quedan on-demand. Auto-abrir la base: --openwelcome "<enterprise>" en Startup.
P7 · Un tile falla "no hallé Export to CSV" (p.ej. 6xd, esquina)
El right-click cae justo al borde del plot → no abre el menú.
Fix (commit 95fda29): export_one reintenta el right-click con offsets hacia adentro (0,0 / ±12 / 0,−18 / −18,0) + ESC entre intentos.
P8 · System1 frío tras reinicio → 1er Save As tarde → cascada
Recién arrancado, el 1er Save As tarda más del timeout → ese canal falla y puede dejar un diálogo trabado.
Fix (commit 62b557e): export_all reintenta los canales FALLIDOS hasta 3 pasadas, calentando entre pasadas (cierra colgados + reactiva hoja + espera 8s). Una pasada caliente recupera.
P9 · Web no muestra capturas nuevas (de la tarde)
Supabase storage.list() devuelve solo 100 objetos por defecto, en orden ascendente. Al pasar de 100 archivos/día, list_captures perdía las capturas nuevas → "en la mañana sí, en la tarde no".
Fix (commit 3e075fe): .list(path, {"limit":2000, "sortBy":{"column":"name","order":"desc"}}) con fallback para clientes viejos. REGLA: todo .list() de storage necesita limit + sortBy explícitos.
P10 · Reportes programados no llegan al cliente
Los briefing Semanal/Mensual crean BORRADORES que requieren aprobación en Report Center; si nadie aprueba (y el cron no lleva --auto-send), se acumulan y no salen. Los RÁPIDO/diario sí salen directos. Además, con la máquina parada (0 rpm), el reporte sale "Máquina detenida" y la IA+RAG se apagan (texto honesto).
Fix: aprobar en Report Center, o poner --auto-send en el cron de Render. La config por máquina (slots/destinatarios) estaba correcta.
P11 · Internet IPv4 muerto en el host (Starlink IPv6 + ZeroTier)
Starlink daba solo IPv6; ZeroTier full-tunnel se tragaba el IPv4; Supabase es IPv4.
Fix: route -p add 0.0.0.0 mask 0.0.0.0 192.168.1.1 metric 1.
P12 · VMware abre la VM en ventana pequeña tras reiniciar
Es solo la vista del host. Lo que importa es la resolución INTERNA del guest (el robot clica coords del guest). Verificar que el guest siga en su resolución (A 1718×839, B 1718×920); si VMware "autoajustó" el guest, recalibrar o desactivar autofit.
Comprobar: en la VM Add-Type -AssemblyName System.Windows.Forms; [System.Windows.Forms.SystemInformation]::PrimaryMonitorSize.
P13 · Live Monitoring "en línea" pero SIN datos nuevos — DNS del host (caso 2026-10-23)
Importante: Live Monitoring (overalls/RPM) lo alimenta el colector Modbus (servicio nssm WatermelonCollectorSGT300A en el HOST), NO las ondas crudas. Si no refresca valores aunque diga "en línea", casi siempre es que el host no puede resolver el nombre de la API (DNS), aunque tenga internet IPv4.

Diagnóstico (en orden)

  1. Supabase live_readings: ¿última lectura vieja? → feed caído.
  2. Log del colector: Get-Content C:\watermelon\collector\logs_sgt300a\svc_out.log -Tail 40. Si se ve Cycle read 72/72 good (Modbus OK) + POST failed ... getaddrinfo failed + Buffered batch (pending count=...) creciendo → es DNS. (Si dijera read failed/timeout sería pérdida del rack Modbus, no DNS.)
  3. Confirmar que SOLO es DNS: Resolve-DnsName <api> falla, pero Test-NetConnection 1.1.1.1 -Port 443 = True (hay internet, falla el nombre).

Ejemplo real del log (lo que se vio)

[INFO]    Cycle read: 72/72 good
[WARNING] POST failed: ... Failed to resolve 'watermelon-api-bpv4.onrender.com'
          [Errno 11001] getaddrinfo failed
[WARNING] Buffered batch (pending count=3189)      <- creciendo, nada sube
Causa: los 3 adaptadores del host quedaron con DNS IPv6 basura (fec0::*, fdd6::* de ZeroTier/Starlink).
Fix (persistente): poner DNS IPv4 reales en el adaptador de internet y en ZeroTier (índices con Get-NetIPConfiguration | ? {$_.IPv4DefaultGateway}): 
Set-DnsClientServerAddress -InterfaceIndex 5 -ServerAddresses ("8.8.8.8","1.1.1.1")   # Ethernet (internet)
Set-DnsClientServerAddress -InterfaceIndex 3 -ServerAddresses ("8.8.8.8","1.1.1.1")   # ZeroTier
Clear-DnsClientCache
Resolve-DnsName watermelon-api-bpv4.onrender.com   # debe devolver una IP
Resultado (log tras el fix): 
[INFO] POST OK: ingested=72 received=72
[INFO] Flushing 20 buffered batches
[INFO] POST OK: ingested=72 received=72 ...   <- vacía el buffer y revive Live Monitoring
Catálogo vivo — cómo alimentarlo
Cada problema NUEVO que aparezca se agrega aquí como P<n+1> con el mismo molde: Síntoma → Diagnóstico (en orden) → Ejemplo real → Fix (código), se regenera el PDF (del HTML, Chrome --print-to-pdf) y se guarda en la memoria del proyecto. 8. Blindaje anti-cruce de datos (detalle)

El robot nunca sube bearings↔gearbox cruzados. Tras exportar cada CSV lee su Point Name y lo compara con el canal esperado (nombre del tile):

def _channel_matches(expected, point_name):   # '1yd' vs '1YD' / '4XA GEARBOX'
    w=(expected or '').upper().replace(' ',''); p=(point_name or '').upper().replace(' ','')
    return True if (not w or not p) else p.startswith(w)
# si NO coincide: borra el CSV, rc=2 → export_all invierte la pestaña (357<->472) y reintenta.
Resultado
Sale 8/8 sea cual sea el orden de las pestañas, y es imposible subir un canal en el lugar de otro. Si el cruce persiste tras 2 inversiones, aborta la hoja sin subir nada.

10. Detección y limpieza de datos cruzados (Supabase)

El CSV que sube el host conserva # point (etiqueta) y # point_name (canal real). Un archivo está cruzado si point=BRG* contiene "GEARBOX", o point=GB* no contiene "GEARBOX". Para auditar/limpiar: listar el día, pedir Range: bytes=0-500 de cada CSV, parsear ambas líneas, y borrar los cruzados con DELETE /storage/v1/object/dynamic_raw body {"prefixes":[...]}. (2026-10-19 se borraron 54 cruzados de SGT300A; quedaron 50 OK.)

Clonar a una turbina NUEVA (checklist)

  1. Crear activo en Supabase (asset + in_service) y en Live Monitoring.
  2. VM: Python + robot (Invoke-WebRequest), armar hoja Export CSV1/CSV2 (4×2), confirmar coords con --grab, desactivar Shutdown Event Tracker, Data Server Automatic, System1.lnk + OpenWelcome.lnk, autologin, export.bat (coords de ESA VM), tarea WM_export.
  3. Host: Python + agente, config.toml (asset, folders UNC con csvgb, service_key), ruta IPv4, cmdkey, upload.bat + WM_upload, colector nssm, run_vm + watchdog + autologin.
  4. Probar export.bat (8/8+8/8 sin CRUZADO) → upload.bat (HTTP 200) → reinicio real hands-off.
